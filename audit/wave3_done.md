# Wave 3 Verification — Synthesis

## Summary

Three adversarial lenses (correctness-trace, spec-conformance, regression-hunt) voted on 8 Wave 3 items: Phase 5.2/5.3/5.4 stealth and discoverability narrowing, Phase 6.2 CR3-scoped memory dump hypercall, Phase 7.1/7.2/7.3 HV introspection resistance plus self-integrity DPC and watchdog auto-unload, and the asm thunk that makes the integrity VMMCALL unconditional. By majority rule, **all 8 items are CONFIRMED (8 confirmed, 0 broken, 0 needs-review)**: every item had its claimed structure and mechanism independently traced to the live source, and even the single `fail` vote on P6.2 came from the regression-hunt lens stipulating that the feature is correctly wired but introduces a kernel deadlock downstream. That deadlock, and seven other regressions ranging from showstopper to nit, are captured below — the items shipped the code the plan said they would, but shipping that code made the driver worse in several specific ways.

### Item notes

- **P5.2** — `scramble_section_names` seeds from `KeQueryTickCount(&tc).LowPart ^ (ULONG)image_base`, writes 8 bytes per `IMAGE_FIRST_SECTION` name, and runs **before** `zero_pe_header` so `e_lfanew` is still live when `IMAGE_FIRST_SECTION` dereferences it. Order and buffer widths match the spec exactly.
- **P5.3** — Block comment at `the_chamber.c:15-38` documents the whole discoverability posture; `IoCreateDeviceSecure` uses `FILE_DEVICE_UNKNOWN` and both the device path and the single `\GLOBAL??` symlink come from `g_chamber_cfg` (launcher-randomized).
- **P5.4** — The only matches for `OpenProcess|NtOpenProcess|ZwOpenProcess|ZwDuplicateObject|ObOpenObjectByPointer` in `driver/` are inside the prohibitive comment in `dump.h`. Live code uses `PsLookupProcessByProcessId` + `KeStackAttachProcess` + `ObDereferenceObject`.
- **P6.2** — Structurally present: `CHAMBER_HCALL_DUMP_CR3` dispatched in `vmexit.c:480`, `KeIpiGenericCall` (not NMI) in `dump.c:382`, VAD walk via `ZwQueryVirtualMemory(MemoryBasicInformation)` at `dump.c:289`, TLV layout per `dump.h:56-60`. See regression R1.
- **P7.1** — Entire body of `npt_hide_hv_image` is `#ifdef CHAMBER_HV_INTROSPECTION_RESIST`-gated (`npt.c:501`), default off. `npt_hide_range` clears P/W/U via `*pde &= ~0x7` at `npt.c:455`. `handle_npf` consults `npt_is_hidden` before `npt_map_page` and injects `#PF` (vector 14, type 3, EC-valid) via `event_inject`. See regressions R2, R3.
- **P7.2** — 5 s KTIMER/KDPC armed in `integrity_init`. FNV-1a 64-bit at `integrity.c:80-89`. DPC calls `chamber_emit_integrity_vmmcall(CHAMBER_HCALL_SELF_INTEGRITY, MAGIC)` unconditionally; bugchecks `0xDEADC0DE` on silent-ignore or hash-mismatch. See regressions R4, R5.
- **P7.3** — `WATCHDOG_MAX_MISSES=5` at `the_chamber.h:193`; `IoQueueWorkItem` with a pre-allocated `IO_WORKITEM` from `start_watchdog`; `watchdog_unload_worker` calls `svm_shutdown_all_cpus` → `svm_offline_cpu` which zeros `VM_HSAVE_PA` then clears `EFER.SVME` (AMD sequence, no VMXOFF anywhere in repo). See regression R6.
- **asm_thunk** — `PUBLIC chamber_emit_integrity_vmmcall`: pushes RBX, moves RCX→RAX (code) and RDX→RBX (magic), emits `vmmcall`, pops RBX, rets — correct MS x64 non-volatile save. `build.ps1:97` iterates both asm sources through `ml64.exe`. Call at `integrity.c:158-159` is not `#ifdef`-wrapped, so the VMMCALL fires every 5 s regardless of the P7.1 flag.

## Regressions introduced

| # | File:line | Severity | Lenses | Mechanism |
|---|---|---|---|---|
| R1 | `driver/dump.c:141` (worker) / `:382` (broadcast) | **showstopper** | correctness-trace, regression-hunt | `KeIpiGenericCall` waits for the broadcast function to complete on **every** CPU before returning. `ipi_park_if_target_cr3` spins at IPI_LEVEL on `g_pause_active` until the originator clears it — but the originator cannot clear it (`dump.c:407`) until `KeIpiGenericCall` returns, which requires every worker to finish. Any VMMCALL where at least one CPU's guest CR3 masks to `g_target_cr3` deadlocks the broadcast at IPI_LEVEL, exceeding `CLOCK_WATCHDOG_TIMEOUT`; self-dump of the operator's own process deadlocks with zero peers. Fix: don't spin inside the IPI worker — arm a per-CPU flag that the vCPU's VMEXIT path honours, or use a bounded-time rendezvous. The comment on `dump.c:96` codifies the misreading. |
| R2 | `driver/integrity.c:94` and `driver/npt.c:501` (P7.1↔P7.2 interaction) | **high** | correctness-trace, spec-conformance, regression-hunt | With `CHAMBER_HV_INTROSPECTION_RESIST` compiled in, `npt_hide_hv_image` clears P/W/U on every NPT PDE covering `DriverStart..DriverStart+DriverSize` — which includes `integrity_dpc_routine`, `chamber_emit_integrity_vmmcall`, `watchdog_dpc_routine`, `IrpDeviceControl`, `UnloadRoutine`, `ipi_park_if_target_cr3`, every HV callback. DPCs fire in guest context; after natural TLB eviction the instruction fetch of `integrity_dpc_routine` takes an NPF, `handle_npf` sees `npt_is_hidden==TRUE` and injects `#PF`, which the guest has no handler for — `IRQL_NOT_LESS_OR_EQUAL` (0x1E / 0x7F) on the first callback after eviction. The `integrity.h:76-80` note that "root context uses the normal kernel VA" is true for `integrity_handle_hcall` but irrelevant to the guest-context DPC prologue that has to execute to reach VMMCALL. Default off, so shipped build unaffected; opt-in feature breaks on contact. |
| R3 | `driver/the_chamber.c:648` (caller) + `driver/npt.c` (never invoked) | **high** | correctness-trace, spec-conformance, regression-hunt | `npt.h:120-121` and `npt.c:546-550` explicitly require a `npt_tlb_flush(vmcb)` broadcast on every per-CPU VMCB after `npt_hide_hv_image`. `npt_tlb_flush` is defined at `npt.c:356` but a repo-wide grep shows **zero callers**. With no flush, per-CPU nested TLBs retain pre-hide (GVA, HPA) translations until natural eviction (ASID rollover, `TLB_CONTROL_FLUSH_GUEST`, vCPU migration) — the hide is a silent no-op on each CPU for the whole TLB-lifetime window. Weakens the P7.1 guarantee the design claims. |
| R4 | `driver/the_chamber.c:201` (watchdog_unload_worker) | **high** | regression-hunt | `watchdog_unload_worker` calls `svm_shutdown_all_cpus` without first calling `integrity_shutdown`. The integrity KTIMER/KDPC remains armed and continues to fire at 5 s period. With `EFER.SVME` already cleared, `chamber_emit_integrity_vmmcall`'s `vmmcall` instruction raises `#UD`; `#UD` at DISPATCH_LEVEL inside a DPC is an unrecoverable kernel-mode invalid opcode fault (0x1E / 0x7F). `UnloadRoutine` (line 480) correctly orders `integrity_shutdown` before `svm_shutdown_all_cpus`; the auto-unload path does not mirror it. |
| R5 | `driver/integrity.c:186` | **high** | regression-hunt | `g_hv_image_size = drv->DriverSize / 2` declares the hashed window as the first half of the driver image — a one-line workaround for the author's own observation that `g_vmexit_count` and the PMU shadow mutate on every VMEXIT. If any mutable globals (`g_vmexit_count`, `g_chamber.kick_counter`, `guest_pmc_snapshot`) land in the first half of `SizeOfImage` on a given build (plausible for a ~4 k-LOC driver with aligned sections and small `.text`), the second DPC fire — 10 s after driver load — reliably bugchecks `0xDEADC0DE,1` because the mutable globals have moved since the first latch. Heuristic one line away from parsing the live `.text` range before `stealth_apply` scrambles section names. |
| R6 | `driver/dump.c:130` (ipi_park_if_target_cr3) | **medium** | spec-conformance | Worker reads `vmcb->save.cr3 & ~0xFFFULL`, but `vmcb->save.cr3` is only written by hardware at VMEXIT. CR3 writes are not intercepted (no bit set in `intercept_vec1/2` at `svm_vmcb.c:310-328`), so the guest can `MOV CR3` arbitrarily between VMEXITs without touching the VMCB field. The IPI is delivered straight to the guest (no INTR intercept), so the worker runs at IPI_LEVEL without a preceding VMEXIT on the target CPU; if that CPU has context-switched since its last VMEXIT, `vmcb->save.cr3` is stale and the park comparison either misses a running vCPU with target CR3 or spuriously parks one that has already switched away. Fix: `__readcr3()` inside the worker (runs in guest, register holds live CR3). |
| R7 | `driver/vmexit.c:574` (#PF injection error code) | nit | spec-conformance, regression-hunt | Injected `event_inject` has error-code-valid=1 but EC bits [32:63] are zero: `W/R=0` forces "read" regardless of `fault_info`, `U/S=0` forces supervisor mode regardless of CPL, CR2 is stale. Comment at lines 568-573 claims U/S=1 ("ordinary user-write PF"), but the word injected has U/S=0 — the comment and the value disagree. A sophisticated introspector that checks CR2 or the EC bits can distinguish the injected fault from a real `#PF`. `fault_info` already carries the real W/R and U/S bits to forward. |
| R8 | `driver/stealth.c:181` | nit | spec-conformance | `scramble_section_names` draws each byte from `'A' + (RtlRandomEx(&seed) % 26)` — 26 values per byte, keyspace `26^8 ≈ 2.1e11` per name. `IMAGE_SIZEOF_SHORT_NAME` can carry 52 values across upper+lower case (`52^8 ≈ 5.3e13`). Still enormous, but smaller than achievable with a wider alphabet. Also, the `RtlZeroMemory` on line 179 is dead code: the loop overwrites all 8 bytes unconditionally on the next statement. |

### Severity rollup

- **1 showstopper** — the dump path deadlocks the box on first use against any running process; this item (P6.2) is `CONFIRMED` by majority only because two lenses read "structurally present" as the pass condition.
- **4 high** — three gated by `CHAMBER_HV_INTROSPECTION_RESIST` (default off), one in the watchdog auto-unload path (reachable on five missed kicks).
- **1 medium** — stale `vmcb->save.cr3` in the dump IPI worker (pairs with R1; only visible once R1 is fixed).
- **2 nits** — cosmetic `#PF` error-code mismatch, reduced section-name alphabet with dead `RtlZeroMemory`.

## Open follow-ups

1. **P6.2 dump path is broken on contact.** Redesign `ipi_park_if_target_cr3` to be bounded-time: set a per-CPU "park requested" flag and have each CPU's next VMEXIT honour it in `handle_vmexit`, rather than spinning inside the IPI worker. Keep the current VAD walk + TLV writer; replace only the pause-primitive. (Addresses R1 and R6 together.)
2. **P7.1 ↔ P7.2 interaction (R2).** Either narrow `npt_hide_hv_image` to the `.text` of pages that no DPC/IPI/IRP callback executes from (keep `integrity_dpc_routine`, `watchdog_dpc_routine`, `watchdog_unload_worker`, `ipi_park_if_target_cr3`, `IrpDeviceControl`, `UnloadRoutine`, and the asm thunk out of the hidden set), **or** make `handle_npf` consult a per-fault allowlist of guest RIPs that may execute from hidden pages. Document the contract in `npt.h` next to the trade-off comment.
3. **Missing TLB flush (R3).** Invoke `npt_tlb_flush` across `g_cpu_ctx` right after `npt_hide_hv_image` returns in `the_chamber.c:648` (and after any future `npt_hide_range`/`npt_unhide_range` from runtime paths). Add a `KeIpiGenericCall`-free broadcast — e.g., a per-CPU DPC that each VMCB's owner picks up on its next VMRUN — to avoid reintroducing R1-style rendezvous hazards.
4. **Watchdog unload ordering (R4).** Mirror `UnloadRoutine`'s teardown sequence in `watchdog_unload_worker`: call `integrity_shutdown` (then any future `*_shutdown` hooks) **before** `svm_shutdown_all_cpus`. Consider factoring the teardown into a single shared function so both paths cannot drift.
5. **Integrity hash coverage (R5).** Replace the `DriverSize / 2` heuristic with a parse of the live PE section headers **before** `stealth_apply` runs: latch a bounds pair for every `IMAGE_SCN_CNT_CODE | IMAGE_SCN_MEM_EXECUTE` section (typically `.text`) and hash exactly those, so mutable `.data` is excluded structurally rather than positionally.
6. **#PF injection fidelity (R7).** Forward W/R and U/S from `fault_info` into the injected `event_inject` EC bits, and update the comment. Decide whether to also forge a plausible CR2 or deliberately leave it stale (document the choice either way).
7. **Section-name entropy (R8).** Widen the alphabet to `'A' + v` and `'a' + (v-26)` for `v = RtlRandomEx % 52`, and delete the dead `RtlZeroMemory` at `stealth.c:179`.

None of the 8 items warrant reopening; the plan code is where it should be. The eight regressions above belong in a Wave 4 fix list or a follow-up patch series — R1 and R4 are reachable in the shipped build and should be addressed first.
